# Hat Trick (sports scores app)

Free, open-source Android app (Expo / React Native): NHL scores, standings, leaders and box scores first, more leagues later. Package `io.github.peakears.hattrick`, repo `peakears/hat-trick`. Not on app stores: users install the APK attached to each GitHub Release, or build it. Everything runs on the device, no backend. Data comes from public APIs. Versions and dates: GitHub Releases and CHANGELOG.md. What the app does: README.

## Architecture (data flows up)

adapters -> domain model -> on-device cache -> Expo app UI

- `src/domain.ts`: league-agnostic types and the `LeagueAdapter` contract. Nothing here knows raw API shapes. Scores, standings and leaders are required; the other methods are optional features (`LeagueFeature`): `SportsData.supports()` says which a league has, the UI hides what leads to a missing one, a call for one fails with `UnsupportedFeatureError` before any request (special events answer empty instead), and the contract suite skips them. `src/registry.ts`: `AdapterRegistry`, adapter by league id.
- `src/adapters/nhl/`: `client.ts` (HTTP), `errors.ts`, `constants.ts`; `raw-types.ts` (zod schemas, types inferred) and `validate.ts` (policy); `mappers.ts` (raw -> domain); `adapter.ts` (fetch -> validate -> map); `__fixtures__/` (recorded responses). Which endpoint has what, and what is still unverified: `src/adapters/nhl/CLAUDE.md`.
- `src/adapters/nba/`: the same layout, from ESPN's keyless site API (scores, standings, leaders, and game, team and player pages; notes in its `CLAUDE.md`). `src/adapters/validate.ts`: the validation helpers both share (`minor()`, `lenientArray()`, `parseWith()`); each adapter's `validate.ts` adds its own error type.
- `src/contract/league-adapter.contract.ts`: suite every `LeagueAdapter` must pass; a new league's test calls `runLeagueAdapterContract()` with fixture-backed adapters. The README's "Adding a league" is the step-by-step guide: keep it true when the adapter contract, the domain's league data (periods, standings bands, leader groups) or registration changes.
- `src/data/`: the only thing the UI calls. `sports-data.ts` (`SportsData`: cache-first reads returning `Fetched<T>` = `{ data, meta }`, offline fallback to last known data, shared in-flight requests, `prune()`), `freshness.ts` (all TTLs), `store.ts`, `types.ts`; `diagnostics.ts` (`DiagnosticsLog`: every adapter warning and failed request that reaches `SportsData`, folded by problem and capped, under its own `diagnostics:v1` key so `prune()` and `CACHE_VERSION` never clear it; Settings › Diagnostics shows and shares it).
- `src/ui/`: code shared by screens, one folder per feature: `data/` (SportsData context, polling, cache store), `common/` (formatting, links), `theme/`, `settings/` (and first-run setup), `scores/`, `game/`, `standings/`, `leaders/`, `team/`, `player/`, `spoilers/`, `notifications/` (reminders, live scores), `updates/`, and `components/`. Each test sits next to the file it tests (`x.ts`, `x.test.ts`). Files called pure have no React Native imports; screen logic goes in a pure file so it can be tested. A new feature gets its own folder rather than a file at the top. League differences reach the UI as data from the adapter (supported features, columns that are empty, position names), never as a league check in a screen.
  - `data/sports-data-context.tsx` creates the one `SportsData` (NHL adapter + `AsyncStorageStore`) and prunes on start. The tabs show the league picked in settings (`data/use-league.ts`, `data/league.ts`, and the league is part of each tab's `usePolled` key so a switch reloads), picked in `components/LeagueBar.tsx` (the league row: Standings and Leaders get it as their header, Scores draws it with its date so each chip counts the day's games from the same `{league}:scores:{date}` entry; logic in `leagues/league-row.ts`); game, team and player pages read their league from the link (`common/routes.ts`: `gameRoute()`, `teamRoute()`, `playerRoute()`, `boxScoreRoute()`, `playsRoute()` carry it; `data/use-page-league.ts` reads it, and a link without one opens the NHL's page), so always link to them through those helpers. Parts only the NHL has so far (spotlight, first-run setup's team picker, reminders, live scores) use `NHL`. Scores' All view (`scores/all-leagues.ts`, `scores/use-league-days.ts`: one `usePolled` per league, under the single-league keys) lists every league's day; `scoresAllLeagues` in settings.
  - `data/use-polled.ts` `usePolled(key, load)`: loads through `SportsData`, re-polls at `meta.staleAt` (`polling.ts`, pure), and only polls the screen shown: it pauses in the background and when its screen loses focus (tabs and stacked screens stay mounted), and checks again, cache-first, on return. `refresh()` is ignored while the data on screen is under 30 s old (`canManualRefresh()`), except when nothing loaded or the data is an offline fallback.
  - Pure helpers, in their feature's folder: `common/format.ts` (Scores order and sections, records, venue, date picker dates at local noon so DST cannot shift the day), `game/` (`goals.ts`, `penalties.ts`: which penalty led to which power-play goal is matched by time, the league does not link them; `stars.ts`, `broadcasts.ts`, `videos.ts`), `standings/`, `leaders/`, `team/` (`team.ts`, `next-game.ts`: the team page's next game card, `favorites.ts`), `player/`, `settings/onboarding.ts` (first-run setup's steps and team picker), `scores/special-events.ts`, `scores/swipe.ts`, `spoilers/`.
  - Scores: a swipe or the week strip (`components/WeekStrip.tsx`, days in `scores/week-strip.ts`) changes the day, and the day you stop on loads 250 ms later (`scores/use-swipe.ts`, `common/use-debounced.ts`), so quick swiping makes no request per day passed. "Today" rolls over at 5am local (`scores/use-today.ts`), so late games stay under Today.
  - Spoiler shield (`spoilers/`): it only changes what is drawn; data is still fetched and cached. Reveals are in memory only. Standings and Leaders are deliberately not shielded.
  - Colours: every colour is in `theme/palette.ts` (pure: a base per scheme, light, dark or pure black, plus the chosen accent); screens get them from `useColors()` in `theme/theme.ts`, never hard-code one. `palette.test.ts` checks each text colour against its background for every scheme and accent (WCAG AA, 4.5:1), and marks that are not text (dots, bars, a selected chip, the selected tab's icon on its `tabSelected` pill) at 3:1, so a new colour or accent must pass it. Text on an accent fill uses `onAccent`. Each league has a colour of its own (`leagueTint()`, a light and a dark shade per league, tested on cards, the page and `surfaceSunken`) for small marks only, never a fill under text; a new league adds one. Fonts: `theme/fonts.ts` (pure: `scoreFont` for scores and big numbers, no `fontWeight`, as the family is the weight), loaded from bundled files by `use-app-fonts.ts` in the root layout; never fetched at runtime.
  - Settings (`settings/settings.ts`, pure, with `settings-context.tsx`, stored under `settings:v1`): a new preference needs a default and a `.catch()` schema field, no version bump. Favourites are `league:team` keys (`team/favorites.ts`: `favoritesFor(league, …)` gives one league's team ids; bare ids saved before favourites had a league are read as the NHL's). Settings are only written when one changes, so "nothing stored" does not mean a fresh install: `loadSettings` counts any other stored key as a returning user (that is how first-run setup skips people who updated). The Settings tab and first-run setup share their rows from `components/SettingsRows.tsx`.
  - Device-only code is kept in one file each, behind pure logic: `notifications/reminders-native.ts` (the only `expo-notifications` code; plans come from `reminders.ts`), `updates/updates-native.ts` (the only file-system and installer code; the flow is `install-update.ts`, with device steps passed in as ports), `game/videos-native.ts` (the only `expo-web-browser` code: videos open on the league's site in a browser tab, never played in the app), `notifications/live-tracker-native.ts` (the only `react-native-notify-kit` code: the live score foreground service and its notifications; in Expo Go and on iOS it is a no-op and `liveTrackingAvailable()` is false, found with `TurboModuleRegistry.get` because importing the library never fails; `index.ts` may only call its JS-only registration, as any call that reaches native code there crashes before native modules are ready, and in Expo Go). Live scores (#114): rules in `live-tracker.ts` (pure: which games to follow, notification text, new goals between checks, when to stop), the loop in `live-tracker-run.ts` (reads through the shared `getServices()` SportsData every 30 s, rereads settings each check, stops when no followed game is left; JS timers stop once the app leaves the front, so its wait and wake lock come from the app's own native module `modules/background-wait`, called only from `background-wait-native.ts`, with the wait's logic in `live-wait.ts`), started by `use-live-tracking.ts` when the app opens near a favourite's game; `index.ts` registers the service before Expo Router starts. TV region: `game/use-tv-region.ts` (setting, or the phone's region via `expo-localization`).
  - Animations use React Native's `Animated` with the native driver (no animation library), and respect the phone's reduce motion setting (`theme/use-reduce-motion.ts`): keep fades, drop movement. `FlashScore` (rule in `scores/score-flash.ts`) pops a live score when it goes up.
  - `components/`: `StatGrid` is the generic stats table (`StatTableView` wraps it for player tables); `TeamLogo` (expo-image, NHL logos are SVG) and `PlayerHeadshot` fall back to an abbreviation or initials and follow the `showLogos` setting.
- `app/`: Expo Router. `(tabs)/`: Scores (`index`), Standings, Leaders, Settings. `game/[id]/index` (game page), `game/[id]/box-score` and `game/[id]/plays` (play-by-play, for a league with `plays`), `team/[id]`, `player/[id]`, `spotlight` (opened from Leaders), `welcome` (first-run setup: the tabs layout redirects there until `onboardingComplete`, and renders nothing until settings load; Settings opens it with `again=1`). Open games, teams and players with `gameRoute()`, `teamRoute()` and `playerRoute()`, never a bare pathname (the league would be lost). The root layout wraps the app in `SettingsProvider` and `SportsDataProvider`; it and the game, team and player pages export an `ErrorBoundary` (`CrashScreen`).
- `app.json` is static Expo config; `app.config.ts` adds `version` and `versionCode` from `package.json`, so never put a version in `app.json`. `android/` is generated by `expo prebuild`, not committed.

## Patterns

- **The field you want may not be in the response you expect.** Goals are not in the box score, special events are not in `/score`, club stats have no team name. Check `src/adapters/nhl/CLAUDE.md` before assuming a field exists, and record a fixture when it does not say.
- **Extras are best effort.** A screen's main request decides whether it loads; anything added from another request (the game page's goals, three stars and special event, the team page's schedule) is caught in the adapter and left out if it fails, and the failure is passed on as a warning (`extraFailed`) so it reaches the diagnostics log. A new extra follows the same pattern, and a test drops it to prove the screen still works.
- **One `usePolled` per source that can fail on its own.** The team page loads `standings` and `team:{id}` separately, and Scores loads the scores and the week's special events separately, so one failure never hides the other's data.
- **Share cache entries instead of fetching again.** The team page and the game page read the Standings tab's `standings` entry; the game page, box score and the team page's next game card (while live) share `game:{id}`; Scores and the game page share `events:{monday}`. Use the same key and the data costs no request.
- **A loading screen shows the shape of what is coming.** Screens show a `Skeleton` layout (`ScoresSkeleton`, `PageSkeleton`, `ListSkeleton`) while their first data loads, never a spinner; a new screen picks the closest one or adds a layout there.
- **Keep slow-changing data out of fast polls.** A live game re-polls every 20 s; data that never changes during a game (special events) gets its own key with a long TTL rather than riding along with the poll. Big data gets its own key too: the play-by-play (`plays:{id}`, about 125 KB) is loaded by the game page's card and its own page, which share it, and never rides along with `game:{id}`, so a failure or a slow load there leaves the rest of the game page alone.

## Rules

- Text the user sees uses Canadian spelling (favourite, colour, Centre, Defence), including labels an adapter makes; code identifiers stay as they are (`favoriteTeams`).
- Only an adapter may touch raw API shapes. Everything above it uses domain types. Team ids are the league's abbreviations (three letters in the NHL; 2 to 4 in the NBA: `NY`, `GS`, `UTAH`), unique within a league only.
- Validation: core fields (ids, teams, scores, game state, standings W/L) use plain zod and throw the adapter's response error (`NhlResponseError`, `NbaResponseError`). Minor fields use `minor()` and are dropped with an `onWarning` call. Lists (box score rows, goals, broadcasts) use `lenientArray()`: one bad item is dropped, not the whole response.
- The NHL API (api-web.nhle.com) is unofficial and unreachable from Claude sessions; ESPN's (NBA) is reachable when the cloud environment's network allows `site.api.espn.com` and `site.web.api.espn.com`, so its fixtures can be recorded here. Anything new needs a recorded fixture first (see Recording a fixture).
- All code outside tests must run in React Native (Hermes): no Node-only or browser-only APIs (e.g. no `AbortSignal.timeout`). Tests use `tsconfig.test.json` (Node types).
- The UI never calls adapters; screens call `SportsData` through `usePolled`. TTLs live in `freshness.ts`.
- Cached entries live under `cache:` keys with a `CACHE_VERSION`. Bump it whenever the shape of a domain type changes, or old cached data is read as the new shape.
- Tests never hit the live API: use recorded fixtures, and simulate drift by editing a fixture in the test.
- API keys (future leagues) are entered by the user and stored with `expo-secure-store`; never commit keys. Keyless leagues like NHL must work with no setup.
- Network calls: the NHL API, ESPN's API (NBA data, only while the NBA is picked; logos and photos from its image server) and GitHub. Video links open nhl.com in a browser tab (the adapter accepts only whole `https://(www.)nhl.com/video/<slug>` URLs), so the app itself fetches no video. Update checks use `api.github.com/repos/peakears/hat-trick/releases/latest` (daily at most; switch in Settings). An APK is downloaded only when the user taps Update, only from this repo's release links (`isReleaseApkUrl`, `isReleasePageUrl`: they match the whole URL, not a prefix, so `..` cannot leave the repo; stored links are checked again on read), into the cache folder (never Downloads), then Android's installer opens; the file is deleted after a failed or cancelled install and on next launch. Keep the README's privacy line true.
- Never commit league logos, player photos or other trademarked assets (their URLs come from the API at runtime). The app icon is original artwork generated by `scripts/icons/generate.py` (rendered by `render.cjs`): change the script, not the PNGs.

## Recording a fixture

Claude cannot reach the NHL API, so the user records responses locally. Give them the exact commands, for example:

```sh
cd src/adapters/nhl/__fixtures__
curl -s https://api-web.nhle.com/v1/schedule/2026-11-17 -o schedule-2026-11-17.json
```

- Name the file after the endpoint: `score-<date>`, `schedule-<date>`, `boxscore-<gameId>-<state>`, `landing-<gameId>-<state>` (state: `final`, `live`), `player-<id>-landing`, `club-stats-<team>-now`, `standings-now`.
- To learn where a field lives, record the same game from more than one endpoint and compare.
- Then: add the file to `FIXTURES` in `nhl.test.ts` with its recording date, write the schema in `raw-types.ts` with a "Verified on <date>" comment, update `src/adapters/nhl/CLAUDE.md`, and commit the fixture with the feature that uses it.

## On-device constraints

- Live updates come from polling: screens while the app is open (cache TTL), and the live score foreground service (dataSync type, limited by Android 15 to about 6 h a day) while a followed game is on, even with the app closed. No server, so no push and nothing can start on its own at puck drop (that would need exact alarms); local notifications are fine (puck drop reminders use `expo-notifications` date triggers; Android may delay them a few minutes). `expo-notifications` bundles Firebase Messaging, which matters for F-Droid/IzzyOnDroid (#27).
- Android/iOS only: the NHL API probably blocks browser (CORS) requests, so an Expo web build would need a proxy.

## Roadmap

Open work lives in GitHub issues, the source of truth; do not copy it here. Design notes an issue does not hold:

- Betting info (#7): opt-in, behind a Settings switch (`showBetting` exists in `settings.ts` but has no row until then), only if a usable source exists (NHL partner odds, else a keyed odds API with the user's own key). Display only: no sportsbook links or affiliate codes (that would make the app commercial). Add a README note: odds are restricted in some places.
- Alternate app icons (#9): colour variants from `generate.py` as `activity-alias` entries; needs a config plugin for `expo prebuild`.
- Redesign for more than one league (#139), on the `redesign` branch (below): league differences reach screens as data from the adapter (period labels, standings bands, leader categories), new colours pass `palette.test.ts` in every scheme, and fonts are bundled, never fetched. Reminders and live scores stay NHL only for now (#132); favourites already carry their league. More leagues (#8): golf needs new domain types; good time to split `mappers.ts` and `settings.tsx` if they have grown.

## Commits and releases

- Conventional Commits (`type(scope): subject`, scope optional), checked by a husky hook (commitlint) and in CI. `feat` is a minor bump, `fix` a patch; `feat!:` or a `BREAKING CHANGE:` footer is major, avoid unless there is a real reason. `docs`, `test`, `refactor`, `perf`, `build`, `ci`, `chore`, `style` cause no release (`perf` is in the changelog).
- release-please (`.github/workflows/release-please.yml`) keeps a release PR open with the next version and CHANGELOG. Merging it creates a draft GitHub Release; the workflow builds the APK, attaches it, then publishes the release (which creates the tag). Never edit the version in `package.json` or `.release-please-manifest.json` by hand.
- APKs: `.github/workflows/android-apk.yml` (`expo prebuild` + Gradle, JDK 17). Releases are signed from the `ANDROID_KEYSTORE_*` / `ANDROID_KEY_*` secrets (never commit a keystore). PRs get a debug-key test APK (artifact, `arm64-v8a` only); it is not a required check. `test-apk.yml` builds the same for any branch, run by hand only (`workflow_dispatch`).
- **Before merging a release PR**, check the docs are current (README features and Settings line, the roadmap here) and the release PR's version and changelog. If something is stale, fix it in a `docs/...` PR and merge that first: merging the release PR publishes immediately.
- **The `redesign` branch** is the integration branch for the redesign (#139): its PRs branch from `redesign` and target it, squash-merged as usual; CI runs on them, and nothing releases from it (release-please only watches `main`). Merge `main` into `redesign` after each release (a merge commit, not a rebase: others branch from it), and when every step is done, one PR merges `redesign` into `main`. Work that is not part of the redesign goes to `main`.
- Workflow: one branch per feature from `main` (`feat/...`, `fix/...`, `docs/...`), one PR each, squash-merged (the PR title becomes the commit, so it must be a Conventional Commit). PR bodies have a summary and a Testing checklist (typecheck, tests, bundle, on a device); tick "on a device" only once the user has seen it. Feature PRs update the README.
- **Before pushing a new branch, check the name is free**: `git ls-remote --heads origin <branch>`. Another Claude session (cloud, or another device) may already have pushed one. If it exists, look at it and ask before overwriting; never force-push over a branch you did not create.
- Open PRs often conflict in `src/ui/common/format.ts`, its test and the docs: merge one, rebase the next onto `main`, keep both sides, run typecheck and tests, push with `--force-with-lease=<branch>:<old sha>`. Two PRs that bump `CACHE_VERSION` to the same number merge with no conflict: the second must bump it again.

## Keeping this file relevant

This file holds what is not obvious from the code: the map, patterns, rules and gotchas, workflow and commands. Feature behaviour belongs in the README and code comments; this file changes only when a path, pattern, rule or gotcha does. Facts about one area go in a `CLAUDE.md` in that folder (loaded only when working there), like `src/adapters/nhl/CLAUDE.md`.

- Do not add history or "Done" lists (git log, Releases and CHANGELOG.md hold them), version numbers, constants (the current `CACHE_VERSION`, TTLs, list sizes), or copies of issue text or feature descriptions.
- When a change alters behaviour, edit the one bullet it affects, in place. Do not append a new paragraph, and delete what has become stale.

## Commands

- `npm install`, `npm run typecheck` (app + tests), `npm test` (vitest), `npm run format` (Prettier, `printWidth` 120; CI runs `format:check`, so run it before committing).
- `npm start` (Expo Go), `npm run android` (native build, needs the Android SDK). Expo Go keeps the old bundle after a dev server restart: press `r` (or shake the phone, Reload) after switching branches. Native features (live scores) do not run in Expo Go: test them with the PR's test APK, or the manual test APK workflow for any branch.
- `CI=1 npx expo export --platform android --output-dir <tmp dir>` checks that Metro can bundle the app without a device.
- Add Expo packages with `npx expo install <pkg>` (matches the SDK). Dependabot (`.github/dependabot.yml`, weekly) sends only patch updates for the SDK-pinned packages (expo, react, react-native and their libraries); an SDK upgrade is done by hand. commitlint skips Dependabot's signed-off commits, whose bodies break the line length rule. If api.expo.dev is unreachable, take the version from `node_modules/expo/bundledNativeModules.json` and `npm install` it. `react-dom` is pinned to the same version as `react`.
- CI installs with Node 22's npm 10 as well as Node 24's, and npm versions disagree about unmet optional peer dependencies in the lock file (a nested TypeScript 5 peer once broke `npm ci`). After changing dependencies, check the lock with `npx -y npm@10.9.2 ci --ignore-scripts --dry-run`; fix a mismatch with `overrides` in `package.json`, not by hand-editing the lock.
- `npm audit` advisories are build tooling only. Do not run `npm audit fix --force` (it downgrades vitest and breaks Expo).
